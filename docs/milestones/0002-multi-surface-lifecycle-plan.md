# Multi-Surface Lifecycle Plan

**Status:** Planned work
**Created:** 2026-08-17
**Starting checkpoint:** `8afcded` on `main`

This is the next implementation plan after the working desktop surface
foundation. It is deliberately separate from the sidebar redesign. The
surface lifecycle must become reliable before the presentation shell is made
more elaborate.

## Starting Point

The current application proves one generated surface end to end:

- specialist evidence is gathered through the existing Aios path;
- a separate groundless model generates HTML from that evidence;
- Aios checks value fidelity before display;
- the widget is visible, movable, and click-through outside its bounds;
- the resident sidebar remains docked below the desktop top bar.

The current implementation has one `experimental_html` field in
`PromptResponse`, one `surface-host` in the frontend, and one
`previous_experimental_html` value in the backend worker. These are the direct
reasons a second request replaces the first and why surface editing is not yet
a real lifecycle.

## Observed Acceptance Results

These results were manually tested after restarting Aios between tests:

| Scenario | Result | Interpretation |
|---|---|---|
| Generate CPU surface | Pass | Single-domain generation baseline |
| Generate RAM surface | Pass | Single-domain generation baseline |
| Move generated surface | Pass | Native overlay and drag baseline |
| Click through outside surface | Pass | Native input-region baseline |
| Explicitly gather CPU and RAM specialists into one surface | Pass | Multi-domain composition baseline |
| Vague CPU plus RAM request | Not reliable | Prompt routing and clarification need a regression test |

Failures must be visible in logs and tests. They must not be hidden by a
legacy panel, a generic widget list, or an invented answer.

## Target Behavior

### Create

A new request that asks for a new widget or surface creates a new backend-owned
surface ID. Existing visible surfaces remain unchanged.

Examples:

- "Show CPU usage" creates surface A.
- "Show RAM usage" creates surface B while A remains visible.
- "Show CPU and RAM together" creates one surface containing evidence from both
  domains.

### Update

An explicit edit request updates the selected or active surface ID in place and
increments its revision.

Examples:

- "Make the CPU widget more compact" updates surface A.
- "Change the current widget to a gauge" updates the active surface.

The update receives the existing HTML, original intent, current evidence, and
the new user request. If the request needs new evidence, the planner gathers it
before composition. If it only changes presentation, the stored evidence may
be reused with its freshness state preserved.

Ambiguous requests must not silently replace or edit a surface. Aios should
ask which surface the user means.

### Close and State

Every surface has an explicit lifecycle state:

- `visible`
- `minimized`
- `closed`

Closing one surface must not affect any other surface or the sidebar. The
backend remains the owner of surface IDs, revisions, evidence snapshots, and
current HTML. The frontend owns only rendering and local pointer geometry.

## Target State Model

Add a backend-owned record similar to:

```text
SurfaceRecord {
    id: SurfaceId,
    revision: u64,
    state: Visible | Minimized | Closed,
    original_intent: String,
    current_request: String,
    generated_html: String,
    evidence: Vec<ToolResult>,
    created_at: timestamp,
    updated_at: timestamp,
}
```

The exact Rust types can differ, but these responsibilities must remain
explicit. IDs and revisions are generated by Aios, not by the model.

## IPC Contract

Replace the single-slot canvas payload with an explicit surface event. The
first version should support:

```text
SurfaceEvent::Created { surface }
SurfaceEvent::Updated { surface }
SurfaceEvent::Minimized { id, revision }
SurfaceEvent::Restored { surface }
SurfaceEvent::Closed { id, revision }
```

`PromptResponse` may carry the conversational answer and a list of events for
the prompt, but it must not carry one anonymous HTML string as the only state.

Each visible surface payload should include:

- `id`
- `revision`
- `html`
- original and current intent
- evidence freshness metadata
- initial or remembered position
- lifecycle state

The frontend must reject an update for an unknown ID or an older revision and
report the error. It must not silently create a replacement surface.

## Implementation Stages

### Stage 0: Lock the Working Baseline

Before changing surface lifecycle code:

1. Preserve checkpoint `8afcded`.
2. Add regression coverage for the passing CPU, RAM, drag, click-through, and
   sidebar behaviors where the environment allows it.
3. Add a focused test for the current replacement behavior so the later change
   proves that replacement has become preservation.
4. Keep the model provider and prompt path unchanged during lifecycle work.

Acceptance: the existing single-surface desktop path remains usable before and
after each later stage.

### Stage 1: Repair Multi-Domain Evidence Collection

Investigate the CPU plus RAM failure before adding surface state:

1. Capture the planner tool calls and returned evidence for a combined prompt.
2. Test `required_specialist_calls` for both `processes.observe_process` and
   `memory.observe_memory`.
3. Test `coverage_gaps` against both tool names and their actual returned text.
4. Ensure the composer receives one evidence index containing every gathered
   specialist result.
5. Add a deterministic test with CPU and memory evidence before using a live
   model.

Acceptance: a combined request reaches the generator only after both domains
are covered, and the generated surface can display values from both.

### Stage 2: Introduce the Surface Manager

Implement the record and lifecycle operations in the Tauri worker or a small
backend module owned by it:

- `create_surface(intent, evidence)`
- `update_surface(id, request, evidence_policy)`
- `minimize_surface(id)`
- `restore_surface(id)`
- `close_surface(id)`
- `list_surfaces()`

Move `previous_experimental_html` into per-surface records. Store the evidence
used to create each surface instead of relying on the last prompt's temporary
tool results.

Acceptance: backend tests create two records, update one, and prove the other
record is unchanged.

### Stage 3: Render Multiple Surfaces

Replace the frontend singleton variables with a `Map<SurfaceId, SurfaceView>`.
The full-work-area transparent canvas remains one native overlay, but it hosts
one DOM element per visible surface.

Required changes:

- render all visible hosts, not one `surface-host`;
- retain each host's local position by ID;
- attach drag and resize observers per host;
- send the union of all host rectangles to the native input-region code;
- update only the host named by an `Updated` event;
- keep the sidebar outside the canvas overlay region.

Acceptance: CPU and RAM surfaces remain visible at the same time, can be moved
independently, and clicks outside both pass through.

### Stage 4: Implement Surface Editing

Add deterministic request intent handling:

- explicit new-widget/new-surface language creates;
- explicit edit/change/update/current language targets the active surface;
- ambiguous references ask the user rather than guessing.

For an update, the generation prompt receives:

- the original request;
- the edit request;
- the previous generated HTML;
- the evidence snapshot used by the existing surface;
- any newly gathered evidence;
- the exact values that must remain faithful.

The updated HTML must pass the same fidelity check. A failed update leaves the
previous revision visible and returns the error. It must not replace a working
surface with a blank or fallback panel.

Acceptance: a user can ask for a layout or style change and see the same
surface ID with a higher revision; another surface remains unchanged.

### Stage 5: One Surface From Many Specialists

Once multi-domain collection works, make the evidence boundary explicit:

- specialists return their normal typed tool results;
- Aios combines them into one evidence index;
- coverage checks every requested domain;
- the generator sees the combined evidence only after coverage passes;
- fidelity checks every displayed value against the combined evidence.

This stage supports CPU, RAM, storage, network, and thermal metrics in one
generated surface without allowing the model to query specialists itself.

Acceptance: a multi-domain test verifies provenance and values from at least
three specialist results in one surface.

### Stage 6: Premium Sidebar Workstream

Do not redesign the sidebar while the surface manager is changing. After the
surface lifecycle is stable, redesign the sidebar in separate visual passes:

1. Write a visual design brief covering typography, spacing, hierarchy, motion,
   states, and desktop integration.
2. Split the current one-file TypeScript renderer into sidebar components and
   state boundaries without changing backend authority.
3. Improve conversation hierarchy, prompt composer, loading/error states,
   evidence presentation, surface list, and settings entry points.
4. Test the sidebar while surfaces are open, minimized, moved, and updated.

The sidebar remains the permanent control surface. Generated surfaces remain
separate presentation windows and must not be folded into the chat layout.

## Error and Fallback Rules

These are acceptance rules for all stages:

- no silent legacy widget-grid fallback;
- no replacement surface after a failed update;
- no invented value when evidence is missing or stale;
- no swallowed native window or input-region errors;
- no ignored IPC event emission errors;
- no model-generated IDs or authority;
- no automatic provider fallback during development;
- platform-specific window modes must report their selected mode and fail
  visibly when unsupported.

Fallbacks that only mask a broken development path must be removed. A
compatibility branch required for a supported desktop backend must be
explicitly named, logged, and tested rather than treated as a silent product
fallback.
